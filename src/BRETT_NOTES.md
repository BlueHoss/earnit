# Environment Variables

Best Practices:

Use \$env/static/public and \$env/static/private for most cases.

These are type-safe and prevent accidental exposure of private variables.

Use import.meta.env.VITE\_\* in components when you need to access public variables directly.

Avoid using process.env in SvelteKit applications. It's not available in all environments and doesn't provide type safety.

For truly dynamic variables that might change at runtime, use $env/dynamic/private or $env/dynamic/public.

Always prefix public variables with VITE\_ in your .env files.

Don't prefix private variables; just use descriptive names like DATABASE_URL.

## Can I use import.meta.env. for private variables?

No, you should not use import.meta.env for private variables in SvelteKit. Here's why:

Security: import.meta.env is primarily intended for use with public variables (those prefixed with VITE\_) and is accessible in both server-side and client-side code. Using it for private variables could potentially expose sensitive information to the client.

Vite behavior: Vite, which SvelteKit uses, only includes environment variables prefixed with VITE\_ in import.meta.env. Other variables won't be available through this method.

SvelteKit's design: SvelteKit intentionally separates public and private environment variables to prevent accidental exposure of sensitive data.

Instead of using import.meta.env for private variables, you should use the following methods:

### For static private variables:

In server-side files only (e.g., +page.server.js, hooks.server.js)

```
import { DATABASE_URL, SECRET_KEY } from '$env/static/private';

console.log(DATABASE_URL);
console.log(SECRET_KEY);
```

### For dynamic private variables:

In server-side files only

```
import { env } from '$env/dynamic/private';

console.log(env.DATABASE_URL);
console.log(env.SECRET_KEY);
```

These methods ensure that:

- Private variables are only accessible in server-side code.
- You get type checking and autocomplete for your environment variables.
- There's no risk of accidentally exposing sensitive information to the client.

### For public environment variables

// In .js, .ts, or .svelte files

```
import { PUBLIC_API_URL } from '$env/static/public';
console.log(PUBLIC_API_URL);

// Or
console.log(import.meta.env.VITE_PUBLIC_API_URL);
```

# The magic of Zod. How to extract

To create a TypeScript interface or type that represents the object generated by your Zod schema, you can use Zod's built-in type inference capabilities along with TypeScript's utility types. Here's how you can do it:

```typescript
import { z } from 'zod';

// Your existing Zod schema
export const userSchema = z.object({
	firstName: z
		.string({ required_error: 'First Name is required' })
		.min(1, { message: 'First Name is required' })
		.trim(),
	lastName: z
		.string({ required_error: 'Last Name is required' })
		.min(1, { message: 'Last Name is required' })
		.trim(),
	email: z
		.string({ required_error: 'Email is required' })
		.email({ message: 'Please enter a valid email address' }),
	password: z
		.string({ required_error: 'Password is required' })
		.min(6, { message: 'Password must be at least 6 characters' })
		.trim(),
	confirmPassword: z
		.string({ required_error: 'Password is required' })
		.min(6, { message: 'Password must be at least 6 characters' })
		.trim(),
	role: z
		.enum(['USER', 'PREMIUM', 'ADMIN'], { required_error: 'You must have a role' })
		.default('USER'),
	verified: z.boolean().default(false),
	isCreator: z.boolean().default(false),
	isFollower: z.boolean().default(false),
	terms: z
		.literal<boolean>(true, {
			errorMap: () => ({ message: 'You must accept the terms & privacy policy' })
		})
		.default(false as true),
	token: z.string().optional(),
	receiveEmail: z.boolean().default(true),
	createdAt: z.date().optional(),
	updatedAt: z.date().optional(),
	roleError: z.string().optional()
});

// Infer the TypeScript type from the Zod schema
export type UserSchema = z.infer<typeof userSchema>;

// If you need a type without certain fields (e.g., for creating a new user)
export type NewUserInput = Omit<UserSchema, 'id' | 'createdAt' | 'updatedAt' | 'roleError'>;

// If you need a type for updating a user (all fields optional)
export type UpdateUserInput = Partial<NewUserInput>;
```

Now, let me explain the key parts of this code:

1. We define the `userSchema` using Zod as you've already done.

2. We use `z.infer<typeof userSchema>` to create a TypeScript type that matches the schema. This `UserSchema` type will have all the fields defined in your Zod schema, with the correct types.

3. We create a `NewUserInput` type using TypeScript's `Omit` utility type. This removes fields that shouldn't be provided when creating a new user (like `id`, `createdAt`, `updatedAt`, and `roleError`).

4. We create an `UpdateUserInput` type using `Partial<NewUserInput>`. This makes all fields optional, which is typically what you want for update operations.

You can use these types in your application like this:

```typescript
import type { UserSchema, NewUserInput, UpdateUserInput } from './path-to-your-schema-file';

// When creating a new user
function createUser(userData: NewUserInput) {
	// Use Drizzle to insert the new user
	// ...
}

// When updating a user
function updateUser(userId: number, userData: UpdateUserInput) {
	// Use Drizzle to update the user
	// ...
}

// When working with a full user object
function processUser(user: UserSchema) {
	// Do something with the user
	// ...
}
```

This approach gives you type safety and autocompletion in your TypeScript code, while still using Zod for runtime validation. The `NewUserInput` and `UpdateUserInput` types are particularly useful when working with your database operations, as they match the shape of the data you'll typically be working with in those contexts.

Remember to adjust the types as needed if your schema changes or if you have specific requirements for certain operations that differ from these general-purpose types.
